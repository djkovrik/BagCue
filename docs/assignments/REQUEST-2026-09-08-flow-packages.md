Если реализация выявит настоящий конфликт, требующий изменения продуктового поведения, зафиксируй его как блокер и запроси решение. Не удаляй старые артефакты, не конвертируй их и не импортируй в новый ledger. Если принадлежность состояния неясна, сначала исследуй сохранённые запросы и историю, не выполняя сброс наугад.

8. Исследуй существующий код и переиспользуй то, что соответствует текущим контрактам. Не переписывай исправные части ради формального старта с нуля. Заново проверь поведение; прежние verified-статусы, receipts и handoffs не являются доказательствами новой итерации. Не поддерживай старые форматы промежуточных доказательств, development-only схемы БД или гипотетические legacy-сценарии.

Применяй профильные `vibe-*` навыки к соответствующим решениям. Навык — источник экспертизы, а не требование создавать отдельного агента на каждый слой или AC. Независимых специалистов разрешено привлекать для конкретных ограниченных подзадач, которые могут выполняться параллельно с полезной работой оркестратора; назначай одного владельца каждому непересекающемуся набору файлов. Связанные слои одной возможности можно реализовать в одном назначении. Обеспечь экспертизу по следующим направлениям:

- структуры KMP-проекта, Gradle, Android/iOS и CI;
- доменной модели и правил объединения;
- SQLDelight и Multiplatform Settings;
- Decompose-компонентов и навигации;
- MVIKotlin Stores;
- локальных уведомлений и platform API;
- privacy-region endpoint через Ktor;
- Firebase Analytics;

- Material 3 UI и адаптивной навигации;
- Compose Resources и локализации EN/RU;
- оригинального логотипа, launcher assets и остальных ресурсов;
- Preview/Paparazzi/golden-инфраструктуры;
- доменных, компонентных, интеграционных и platform-тестов.

Реализуй все 51 acceptance scenario и 12 quality gates согласно их применимости. Группируй связанные AC в ограниченные capability packages по общему пользовательскому результату, компоненту или агрегату данных. Внутренние зависимости пакета реализуй в порядке зависимостей; внешние зависимости должны быть verified или явно waived. Каждый AC сохраняет собственные обязательные verification surfaces.

Первый пакет должен подключить настоящий production root BagCue и дать достижимый из него сценарий каталога: сохранить значение, прочитать его и восстановить после перезапуска. Каждый следующий пакет интегрируй в этот root до перехода к следующему. Изолированные компоненты и previews не доказывают работающий пользовательский flow. Записывай entry-point, navigation и restart evidence через `integrate`; число integrated flows показывай отдельно от числа verified AC, не выдавая их отношение за процент готовности приложения.

Используй `delivery-work.py` с сохранёнными JSON-запросами для package/scope/assign/check/handoff/ingest/bind/integrate. Регистрируй назначения до правок. Запрашивай компиляцию и минимальный значимый поведенческий тест сразу после готовности кода, до финального handoff. Handoff содержит только assignment-local baseline/result и собственный changedFiles; глобальные handoffs не поддерживаются. Не вычисляй fingerprints и накопленные списки изменений вручную.

Targeted receipts требуют зарегистрированного `inputScopeId` и start/end input fingerprints. Scope должен включать проверенные транзитивные зависимости; build/spec/instruction inputs добавляются по контракту скилла. При неясных зависимостях регистрируй консервативный scope всего репозитория, а не targeted receipt без scope. Глобальные интеграционные и audit-time проверки используют `kind: integration`; покрывающий post-audit прогон — `kind: final`. Используй текущие контракт и helpers, не воспроизводи прежние форматы.

Ключевые ограничения, которые нельзя потерять:

- Android — обязательный целевой продукт, application ID `com.sedsoftware.bagcue`.
- iOS-приложение с bundle ID `com.sedsoftware.bagcue.iosApp` должно компилироваться и линковаться на macOS CI.
- Данные локальные, без аккаунта и синхронизации.
- EN — базовая локаль, RU — дополнительная; выбор языка только системный.
- Firebase Analytics выключена по умолчанию и включается пользователем в настройках.
- Не собирай рекламный идентификатор и не связывай Analytics с рекламными функциями.
- Единственный рекламный провайдер — Yandex Mobile Ads, без mediation.
- Privacy flow должен выполняться до инициализации Yandex SDK и соответствовать AppSpec и `docs/PRIVACY-REGION-ENDPOINT.md`.
- Реальная реклама разрешена только на Android после полного завершения сборов без пропусков, не чаще одного раза для одной завершённой сессии, в виде неблокирующего адаптивного inline-баннера ниже основного результата и кнопки «Готово».
- Никакой рекламы в активном списке сборов, редакторах, истории, настройках, уведомлениях, consent-диалоге или после завершения с пропущенными.
- Interstitial, rewarded, sticky и app-open форматы запрещены.

Production-рекламный блок Android уже создан пользователем:

- Format: adaptive inline banner; в кабинете РСЯ блок имеет тип «Баннер».
- Android application ID: `com.sedsoftware.bagcue`.

Зафиксируй этот ID как явное пользовательское решение в delivery ledger и подключи его через документированную Android release-конфигурацию:

- реальный ID разрешён только в Android production/release-сборках;
- debug, tests, previews и screenshot tests не должны выполнять реальные рекламные запросы;

- не передавай ad unit ID в Firebase Analytics и не записывай рекламные события, пользовательские данные или privacy payload в логи.

QG-009 больше нельзя считать заблокированным только из-за отсутствия Android ad unit ID. Закрывай его полностью только после проверки конфигурации РСЯ и контролируемого diagnostic-теста на физическом Android-устройстве. Если такая проверка недоступна, оставь только эту непроверенную часть как точный внешний блокер. Не приравнивай наличие ID к подтверждённому production-показу или владению кабинетом.

Коммить реальные Firebase service configuration files напрямую как `androidApp/google-services.json` и `iosApp/iosApp/GoogleService-Info.plist`; не создавай для них GitHub Secrets и не восстанавливай их из base64 в CI. Перед коммитом проверь соответствие application/bundle ID. Не подставляй фиктивные Firebase, signing, Google Play или другие credentials. Не заявляй внешний gate выполненным без проверяемых доказательств.

UI реализуй по утверждённым SCREEN/FLOW-файлам. Используй Lazyweb до проектирования интерфейса. Рано проверь сборку и scanner на небольшом production preview, затем компилируй previews вместе с изменяемым UI. Record/inspect/verify выполняй для затронутых goldens на границе стабильного экрана или capability package и после визуальных изменений, а не после каждого AC или handoff. Сохрани light/dark для каждого обязательного primary state; дополнительные locale/font/device комбинации выбирай по рискам и pairwise-покрытию, сохраняя все объявленные риски. Отложенный golden-test оставляет AC implemented-unverified.

После стабилизации primary screens выполни один полный Lazyweb review SCREEN-001…SCREEN-011 в числовом порядке — ровно один экран/report в работе. Повторяй только существенно изменённые экраны или экраны с нерешёнными findings. Пока отчёт ожидается, продолжай независимую работу. Перед завершением остаются обязательными полная golden verification и проверка согласованности всех экранов. Нормативные продуктовые решения из AppSpec имеют приоритет над внешними референсами.

Используй `resume-delivery.py --compact` после перерыва и compaction, перечитывай изменившиеся входы и действительно утраченный контекст. 1. Закрой все локально выполнимые AC и repository gates доказательствами.
2. Честно пометь недоступные внешние/platform/release gates как `blocked-external`, где это допускается протоколом, с точными инструкциями для их закрытия.
3. Отдельно укажи, подтверждены ли кабинет РСЯ, принадлежность блока `R-M-19857241-1` и реальный показ на физическом Android-устройстве.

7. При `GAPS` исправь замечания и проведи новый независимый audit с новым request ID.
8. После свежего `PASS` выполни покрывающий все verified obligation/surface пары глобальный прогон с `kind: final`, начатый после завершения аудита. Сгенерируй отчёты из актуального ledger и запусти `validate-delivery-ledger.py`. Не переноси scoped reuse промежуточных проверок на финальное подтверждение готовности.
